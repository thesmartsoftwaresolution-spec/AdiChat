## 2. Stitch ZIP review and source-of-truth rules

The uploaded archive contains 35 screen groups and 140 HTML variants: -
35 screens × mobile/desktop × light/dark = 140 variants. - Each HTML
design has a corresponding `screen.png`. - The archive includes two
additional design-system markdown files. - The exported screens are
standalone HTML using Tailwind CDN, Google Fonts and Material Symbols;
they are a design/export artifact, not a production React application.

**Implementation instruction:** inspect and reuse the exact Stitch
HTML/CSS structure and assets as the basis for React components. Convert
markup into maintainable components and wire real behavior/data. Do not
substitute a fresh design system, change spacing, typography, component
proportions, colors or layouts for aesthetic preference. Do not ship
Tailwind CDN as a production dependency; migrate the required
utility/style rules into the project build.

### 2.1 Actual visual baseline (approved)

The user explicitly selected "actual ZIP". Therefore the actual screens
take precedence over the earlier strict palette in
`00_Stitch_UI_Prompts.md`.

Observed in the HTML export: - Dark canvas/background token commonly
`#101412`. - Dark primary accent commonly `#77DAA4`. - Light backgrounds
commonly `#FCF8F8`, with some `#FFFFFF`. - Light primary commonly
`#004327`. - Actual screenshots show a warm near-white light canvas and
charcoal/green dark surfaces.

The two bundled `DESIGN.md` files conflict internally and with one
another: - `adichat/DESIGN.md` YAML token values differ from its prose
description. - `adichat_design_system/DESIGN.md` YAML values differ from
its prose description. - The earlier `00_Stitch_UI_Prompts.md` idealized
pure white/black palette is not the selected visual baseline.

**Resolution:** use actual HTML computed/static CSS values and matching
screenshots as the implementation authority. Where tokens are
inconsistent, inspect the relevant screen's actual CSS and screenshot;
do not silently force the earlier pure-white/pure-black palette.
Consolidate a canonical `src/styles/tokens.css` from the values that are
actually used across the 140 screens. Preserve screen-specific
exceptions only when present in the source design. Document any
unresolved token conflict in the build report.

## 4. Supabase client and environment

Create one typed browser client. Use only public client configuration in
Vite: - `VITE_SUPABASE_URL` - `VITE_SUPABASE_ANON_KEY` or
`VITE_SUPABASE_PUBLISHABLE_KEY` (choose one naming convention and use it
consistently throughout code/deployment; do not require both).

Never put `service_role` keys, database passwords, Cloudflare API
tokens, Workers AI credentials or other secrets in `VITE_` variables.
The Supabase service-role key must never be exposed to the browser or
committed to GitHub.

Recommended auth: Supabase Auth email/password, session persistence via
the supported client library, recovery flow via email redirect, and
route guards based on the authenticated session plus server-verified
role/status.

## 5. Cloudflare Workers AI integration

### 5.1 Provider decision

Cloudflare **Workers AI** is the selected inference provider. This is
not a generic provider choice and should not be replaced with
OpenAI/Gemini by default.

### 5.2 Safe request flow

1.  Browser calls an application-owned Cloudflare Worker/Pages Function
    endpoint.
2.  Endpoint validates the Supabase access token/session and verifies
    the caller can access the conversation and assistant.
3.  Endpoint loads the assistant's saved configuration and applies
    server-side limits.
4.  Endpoint invokes Workers AI using the Cloudflare AI binding
    (`env.AI`) and a configured model identifier.
5.  Endpoint streams or returns the model response to the browser.
6.  The application persists the user and assistant messages through the
    authorized backend path and emits realtime updates.
7.  The endpoint records usage and returns structured errors without
    exposing internal secrets.

Use the official Workers AI binding/configuration model supported by the
deployed Cloudflare runtime. Do not assume a model identifier before one
is selected and checked for availability in the target account/region.
Keep `AI_MODEL_ID` as a server-side setting/configuration key (not a
Vite variable). If the deployed binding requires a model ID in
code/config rather than a secret, keep it in Worker configuration and
document it.

Cloudflare AI Gateway is optional and is not a substitute for Workers AI
itself. Add Gateway only if the owner later chooses its
observability/routing features and confirms the required account
configuration.

### 5.3 AI security and reliability

-   Authenticate every request.
-   Enforce owner/participant/admin authorization server-side.
-   Apply per-user/per-assistant rate and daily usage limits.
-   Bound input size, output tokens and execution duration.
-   Treat system instructions as server-controlled; user-editable
    assistant instructions are untrusted content and must be delimited.
-   Do not allow prompt content to reveal secrets or bypass
    authorization.
-   Avoid logging full sensitive prompts by default; log request IDs,
    user/assistant IDs, model ID, latency, token/usage metadata where
    available, and outcome.
-   Return safe error codes for quota, unavailable model, timeout,
    invalid request and permission denial.
-   Confirm streaming protocol and Workers AI model capabilities during
    integration; do not promise streaming if the selected model/runtime
    path does not support it.

### 5.4 Model selection pending

The provider is confirmed; the exact model is not. Admin - App Settings
may show the configured model identifier as a setting, but arbitrary
model IDs must be validated against supported Workers AI models before
save/deploy. Record the final choice in deployment configuration and
release notes.

## 6. Supabase Realtime strategy

Use Realtime subscriptions for: - New/updated/deleted messages in
conversations the user is authorized to access. - Relevant conversation
metadata and unread counters. - Group membership changes. -
Presence/typing where appropriate.

Typing events should be ephemeral and rate-limited; do not persist every
keystroke. Presence is best-effort and must respect privacy settings.
Use server timestamps for durable events. Implement
reconnect/resubscribe and duplicate-event handling.

## 7. Storage strategy

Use private buckets for: - `avatars` - `chat-attachments` -
`voice-notes` - `developer-assets`

Suggested path partitioning: - `avatars/{user_id}/{file_id}` -
`chat-attachments/{conversation_id}/{message_id}/{file_id}` -
`voice-notes/{conversation_id}/{message_id}/{file_id}` -
`developer-assets/{file_id}`

All upload metadata must be validated: MIME type, file size, allowed
extension and ownership. The actual limits are configurable through
Admin - App Settings; initial numeric limits are not specified in the
source and must be chosen before production. Use signed URLs or
authenticated access for private media. Developer profile assets may be
publicly readable if the developer page is public, but only admins may
write them.

## 8. Security requirements

-   Enable RLS on every user-facing table.
-   Deny by default; write explicit SELECT/INSERT/UPDATE/DELETE
    policies.
-   Use membership checks for conversation and group data.
-   Never trust client-supplied `user_id`, role, owner, sender or status
    fields; derive identity from `auth.uid()` in policy/function
    context.
-   Keep admin authorization in trusted tables/functions and check it
    server-side.
-   Protect role changes, account suspension/ban, moderation and
    settings mutations.
-   Bootstrap Super Admin once, through a trusted one-time process after
    Adeel Bhatti's Supabase Auth account exists.
-   Store audit events for privileged mutations.
-   Validate and sanitize all user-generated text and links.
-   Rate-limit login-adjacent, search, message, upload, report and AI
    endpoints as appropriate.
-   Use secure HTTP-only cookies if implementing a custom server
    session; otherwise use Supabase's supported auth flow.
-   Configure CORS narrowly for the production application origin.
-   Do not expose stack traces, SQL errors or secret values to end
    users.

## 10. Build and Cloudflare deployment

-   Build command: `npm run build`

-   Output directory: `dist`

-   Package manager: npm.

-   Commit `package-lock.json`; remove `bun.lock` and `bun.lockb` if
    present.

-   Root `.npmrc` must contain exactly:

    ``` ini
    legacy-peer-deps=true
    ```

-   Configure SPA fallback using `public/_redirects` containing:

    ``` text
    /* /index.html 200
    ```

    or the equivalent Cloudflare routing configuration.

-   Confirm Node version compatibility and pin a supported version in
    project configuration.

-   Cloudflare deploys from GitHub `main`.

-   Add Vite public variables before build; add Worker secrets/bindings
    in Cloudflare dashboard/runtime configuration.

-   Verify direct route refresh, asset paths, environment configuration
    and production build logs.
